# v8.7.1 pre-claim delivery stall

Date: 2026-09-26
Mode: execute-ready / source fix and regression verification
Base: v8.7.1, `1477d06e1`; isolated checkout `/var/tmp/ccb-ask-stall-20260926`.

## Observed incident

Read-only trace of `job_4355afb8bbcb` in the Nozeli project confirmed one
pending OMP attempt, no execution and no reply. Worker1 was healthy/idle with
one queued mailbox event. `mailbox_kernel/service_runtime/summary.py` derives
`blocked` whenever queue depth is positive and there is no active event; that
word alone does not identify a broken claim, lease, or FIFO.

The bound pane was alive at the default empty OMP composer after a Bun crash.
The production `DraftTarget.observe()` returned `unknown/composer_unavailable`.
Its native `inspect` connection failed. The configured endpoint was still an
owner-only socket, but no process listened on it. The restarted process had
the matching actor, launch id and socket environment, and its completion log
contained a fresh `extension_ready` event. Completion-extension readiness did
not establish editor-bridge readiness.

Connecting to that same abandoned endpoint yielded:

| Client | Result |
| --- | --- |
| Python Unix socket | ECONNREFUSED |
| Node node:net | ECONNREFUSED |
| Bun 1.3.14 node:net | ENOENT |

`provider_backends/omp/composer_bridge.py` accepted only ECONNREFUSED for stale
socket reclamation. With Bun it returned without starting the editor server.
Pre-claim draft protection consequently kept returning false forever. The 180s
timer only applies to confirmed idle nonempty input; it cannot repair an
unavailable bridge and must not turn unknown input into permission to clear.

## Source fix

- Accept Bun's ENOENT as well as ECONNREFUSED only after observing an existing
  same-owner socket. Recheck socket type, owner, inode and device before unlink.
  Successful connections, regular files and symlinks are never displaced.
- Distinguish missing/refused bridge errors as `composer_bridge_unavailable`.
- Retain a cached reason even when the first binding resolution fails.
  Expose the current queued job's guard reason, timer and clear-attempt state
  through `ccb queue`; observation commands never capture or clear the editor.
  Cleared/cancelled/changed queue heads do not display stale guard evidence.
- Keep strict FIFO, provider-turn prerequisites, fixed 180s and unknown safety.
  No timeout-based injection, new completion detector or automatic resubmit.
- Recognize ASCII right-padding after the exact Codex empty placeholder at
  its initial cursor position. Official 0.146.0 and 0.156.1 `empty.snap` contain
  this padding; the previous exact string comparison misclassified it as a
  draft, then could not confirm empty after clear. The regression fails before
  this change and passes afterwards; additional real text still stays nonempty.
  This retains the existing exclusion of a user typing the literal placeholder.

## GitHub #356 and remaining boundary

### Additional Codex-to-Codex investigation (2026-09-26)

In a second disposable project, both a fresh Codex-to-Codex result chain and
a result chain after restoring the same sessions passed on Codex 0.155.1.
Killing only the test helper process then reproduced the exact issue error:
`unexpected argument '<session UUID>'`, `Usage: codex resume ...`, exit 2.
The saved command's final segment accumulated five `resume <same-id>` suffixes.

Root cause: CCB's launcher generates `--dangerously-bypass-hook-trust`, but
`start_cmd_runtime/rewriting.py:_continuation_subcommand_index` does not know
that flag. It stops before reaching the existing `resume`; each binding update
appends another continuation instead of replacing it. Automatic recovery reuses
the polluted command, fails again and backs off. This is independently proven
locally, not just an old Codex incompatibility. Two regression tests fail before
the fix: repeated binding idempotence and normalization of already polluted
commands. The implemented minimal change recognizes this CCB-generated flag
without changing permission policy or dropping legitimate option values.
No retry bypass or timeout-based editor clearing is needed for this cause.

Source chain:

- `lib/provider_backends/codex/launcher_runtime/command_runtime/service.py:224`
  adds the hook-trust flag to the automatic-permission launch arguments.
- `lib/provider_backends/codex/session_runtime/binding_runtime.py:167`
  builds and stores the updated resume command during session binding.
- `lib/provider_backends/codex/start_cmd_runtime/rewriting.py:71` rebuilds the
  continuation; the missing zero-argument flag at line 92 caused accumulation.
- `lib/ccbd/supervision/recovery.py:68` handles probing/retry; the backoff and
  circuit prevent endless rapid retries but cannot correct malformed arguments.
  Local logs showed three recovery attempts, not absence of recovery.
- `lib/ccbd/services/runtime_recovery_policy.py` gates background recovery on
  degraded, recoverable runtime health. Healthy panes with unknown composer
  observations do not enter that recovery path; the draft gate keeps the queue
  head pending instead. This separate class still needs exact observation
  evidence in the reporter's environment.
